# Releasing Template

How a Template release is made and what it needs. Contribution rules (scopes, branches, changelog bullets) are in
[CONTRIBUTING.md](../CONTRIBUTING.md).

## Version

`mygo.json` holds the version; only `python3 scripts/bump.py <version>` edits it. The script also turns
`## [Unreleased]` of `CHANGELOG.md` and `CHANGELOG.zh.md` into the new version's section with the date.

## Releasing

The baseline has no publishing pipeline: signing, notarization and update hosting are not configured, and the
manual `package.yml` workflow (Actions > Package > Run workflow) only builds unsigned development packages.
A product that ships adds, before its first release:

1. Signing and notarization credentials for each target platform, and the update signing key pair (public key in
   the product configuration, private key in a secret store with an offline backup).
2. A downloads host (for example `https://dl.example.com`) with per-target update manifests and signed archives
   generated by MyGo.
3. A `release.yml` workflow of its own: verify (`scripts/check.sh --cross`, changelog sections for the version),
   build and sign, publish, then tag `vX.Y.Z` on the built commit and create the GitHub Release from the changelog
   section. It runs in a GitHub environment named `release` that has a deployment branch policy allowing only
   `main`; the credentials of step 1 are secrets of that environment. List the secrets in the table below.

| Secret | Content |
|---|---|
| (none yet) | Fill in when the release workflow is added |

4. A security review `docs/security/<version>-review.md` for the version ([security/README.md](security/README.md)).

Until then `scripts/release.sh` builds local packages only and never uploads.

## When a release is wrong

Do not announce it. Pull the broken build from the downloads host and its update manifests, publish a fixed
version through the same steps, and rotate any credential that may have leaked before replacing the secret.
